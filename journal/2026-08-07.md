# 2026-08-07 — TanStack/router #7991 triage: client disconnects reported as 500

Continuity with the react-router #15377 / #15382 thread — same theme (client disconnects in SSR streams), now in TanStack Start.

**The issue.** When a client goes away mid-request (reload, closed tab, aborted fetch), Start's cancellation propagation rethrows `request.signal.reason`, which reaches h3's `toResponse` at `request-response.ts:141` with no config. h3 marks it `unhandled` → `console.error` + a 500, once per abandoned request. Routes with several long-lived connections per page turn a single reload into a burst of unhandled 500s.

**Why I filed a triage comment, not a PR.** The obvious "make abort a 499" change breaks two cancellation tests in `createStartHandler.test.ts` that abort the request and assert `status === 500` — deliberate, covered behavior, not an oversight. And the reporter offered two design directions, not one fix. Picking the status code and logging policy is a maintainer contract decision (Sean Cassiere / Manuel Schiller). So the value here is a precise, verified triage that confirms the mechanism, flags the tested-contract wrinkle, and lays out both options — with the fix already implemented locally, ready to ship once they pick a direction. Better a clean triage than a PR that guesses the contract.

Verified everything against `main` via the API before commenting: mechanism (h3_toResponse call site), the two 500-on-abort tests, and that the issue is still free (no linked PR).
